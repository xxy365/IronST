## 1. 三态定义（本表刻意分开，不得混为一谈）

| 状态 | 含义 | 判定依据 |
| --- | --- | --- |
| **登记** | 有可稳定复现的记录（测试 / 缺陷条目 / 源文件注释） | 能指出具体文件与位置 |
| **修复** | 源码已改并已提交 | 有 commit hash |
| **验收** | 有断言覆盖该行为，且全量回归通过 | 有测试文件 + 该状态下的全量通过数 |

> **三者互相独立**：登记 ≠ 已修；已修 ≠ 已验收；已验收但没登记 = 无回归保护。

## 3. 本次审计补强的根因（源码实证）

### 3.1 F3 —— 初始值在**前端边界**就丢了

链条完整，四处证据：

1. 语法与 AST **确实解析**了初始值：`ParseTreeToASTVisitor.cs:267`、`:288`、`:300`
2. 但 `VariableInfo` 记录**没有初始值字段** ——
   `AnalysisResult.cs:160-167` 的字段是
   `Name, TypeName, POUName, VarBlockKind, FilePath, Line`
3. 因此 `InitialValue` 在 `IronST.LLVMCodeGen` / `IronST.BytecodeGen` **全仓零命中**
4. 全局一律零初始化：`IRGenerator.cs:318` `var zero = CreateZeroConstant(irType);`

> **影响**：`VAR_GLOBAL x : INT := 5;` 静默变成 0，**无任何诊断**。
> 既有 `ParseTreeToASTVisitorTests.cs` P0_1/P0_2 只断言 AST 保留了初始值，
> 没有一条断言它被生成 —— 这正是「有登记无验收」的典型。

**v1 决策（已定）**：**暂不修**。代价必须显式承担，不得靠默契 —— 见契约
[`docs/增量编译契约.md`](./增量编译契约.md) §7 中的「多文件构建不保证保留显式初始化」声明，
本项验收标为**挂起**，不得记为「已解决」。

#### 3.1.1 F3 修复记录（2026-10-22）

> **决策订正**：原先的「v1 不修」在 **2026-10-22** 被用户推翻（“F3 这个也测试驱动修复”）。
> 下文是**当时的理由**，保留作为决策轨迹；实际状态见本小节。

**修复链路**（四层，每层各补一处）：

| 层 | 改动 | 文件 |
| --- | --- | --- |
| 前端（求值） | 新增 `ConstantEvaluator` —— 编译期常量求值（整数 / 实数 / 布尔 / 枚举成员 / 一元负号） | `IronST.Frontend/Analysis/ConstantEvaluator.cs` |
| 前端（承载） | `VariableInfo` 增 `ConstantInitializer? InitialValue` 字段；语义分析对**所有**变量初值做 `InferType`，对**全局**初值额外做常量求值 | `AnalysisResult.cs` / `SemanticAnalyzer.cs` |
| IR（全局） | `GlobalVariable` 增 `HasExplicitInitializer` 标志；`RegisterGlobalVariables` 把初值落成 IR 常量 | `IronST.IRBuilder/IR/GlobalVariable.cs` / `IRGenerator.cs` |
| IR（局部） | 局部 `VAR` 初值在**序言**里发射一条 `store`（每次调用重新生效） | `FrameBuilder.cs` |
| IR（FB 成员） | FB 成员的初值在**实例创建处**（调用方）写一次 —— 不是 FB 的序言，否则会冲掉跨调用状态 | `FrameBuilder.cs` / `IRGenerator.cs` / `CodeGenContext.cs` |

**关键设计决定**：

1. **字节码零变动** —— 没写初值的全局**不发射任何指令**（`HasExplicitInitializer` 标志区分
   “零初始化”与“显式写了 `:= 0`”），既有程序的产物**逐字节不变**。
2. **全局初值必须是编译期常量**（IEC 61131-3 硬性要求）—— 非常量报 **E2017** 错误；
   是常量但类型暂不支持（字符串 / 数组 / 结构体）报 **E2017 警告**并忽略。
3. **FB 成员初值只支持常量** —— 初值在**实例创建处**（调用方）求值，那里看不到 FB 自己的成员。

### 3.3 F5 —— 结构体比较（修复前：身份比较）

`IronST.Runtime.Shared/BcValue.cs:308-330` `Eq`：

```csharp
ValueTag.Struct => a.SubTag == b.SubTag && a.IntValue == b.IntValue,
```

`IntValue` 对结构体承载的是**实例标识**，因此 `=` 比较的是「同一个实例吗」，
不是「字段值相等吗」。IEC 61131-3 期望结构体按值比较。

**修复前这是 P1**：必须先确认 IronST 语言规范如何规定，再决定修不修 —— 不可在契约冻结前擅自改。
2026-10-23 已按方案 A 修复（按值比较，见 §3.3.2）；本节保留修复前的运行期事实。

#### 3.3.1 编译期实测（2026-10-22）—— 修复前运行期语义**不可达**

上面记的是**运行期**语义（`BcValue.Eq`）。但从**编译期**入口实测，结构体 `=`
**根本编译不过**，因而修复前那段运行期代码**到不了** —— 两者是**不同层次**的缺陷，
不要混为一谈。

**实测**（CLI，源文件：两个字段值完全相同的结构体实例做 `=`）：

```
$ ironst run structcmp.st
Unhandled exception. IronST.LLVMCodeGen.Exceptions.CodeGenException: 不支持的比较类型: STRUCT
   at IronST.LLVMCodeGen.CodeGen.ExpressionEmitter.EmitComparison(BinaryExprNode bin) in .../ExpressionEmitter.cs:line 419
   at IronST.LLVMCodeGen.CodeGen.ExpressionEmitter.EmitBinaryExpr(BinaryExprNode bin) in .../ExpressionEmitter.cs:line 298
   ...
退出码 127
```

即：**IR 生成阶段**就抛 `CodeGenException`，编译器**未**给诊断、**未**给退出码 `1`。

> **对「工业可用」判断的影响（修复前）**：F5 的用户可见症状曾是**编译器崩溃**，
> 而**不是**登记在案的「静默比较出错」。前者吵闹（易发现）、后者安静（易漏过）。
> 但**若只修运行期 `BcValue.Eq` 而不同时放开编译期**，F5 就会从「崩溃」
> **退化成**「静默按实例身份比较」—— 那是**更坏**的失败模式。
> ⇒ 当时判断两处必须**同时**处置，顺序不可颠倒；本轮改用第三条路：IR 完全降级为逐字段比较，使该运行期路径不可达（§3.3.2）。

**退出码契约不一致**另见 §7（README §18 承诺编译错误为 `1`，实测为 `127`）。

#### 3.3.2 修复（2026-10-23，方案 A：按值比较）

本轮不再把 F5 视为「要么改 `BcValue.Eq`、要么前端拒绝」的二选一：
IR 已完全降级为**逐字段/逐元素**比较，使整结构体 `IEQ` / `BEQ` 对该特性
**不可达**。因此 **没有修改** `BcValue.Eq` 的结构体分支，标量比较和既有
聚合赋值路径不受影响。

**前端准入**（`SemanticAnalyzer.InferBinary` → `CheckStructComparison`）：

- 只允许 `=` / `<>`；两侧必须是**同一个命名结构体类型**；
- 两侧必须是可寻址左值（变量、字段、数组元素）；结构体函数返回值等直接拒绝；
- 递归检查字段：`REFERENCE` / `STRING` / `WSTRING`（含嵌套、数组元素）报 `E2003`；
- 顶层数组整体比较报 `E2003`（结构体**字段**里的数组仍逐元素展开）；
- 全局/外部聚合暂报 `E2003`（全局聚合存储是独立缺陷 A8，见 §3.10）；
- 诊断带字段路径，例如 `inner.p`、`a[]`。

**IR / 字节码降级**（`ExpressionEmitter.EmitStructComparison`）：

- 字节码把结构体和数组**扁平化**到 VM 栈槽；寄存器里的“聚合值”是基址槽号，
  不是 `ValueTag.Struct`，因此不能对结构体整体 `load` / `icmp`；
- 先用 `EmitAddress` 求地址，再按字段/元素 `GEP + load + icmp/fcmp`：
  `=` 用 AND 合取，`<>` 用 OR 析取；嵌套结构体和数组递归处理；
- 每个「结构体类型 + 比较方向」生成一个私有 `i1 (ptr, ptr)` helper
  （`__st_cmp_N`），helper 缓存放在 `CodeGenContext`；
- 不把整棵比较树内联到调用者，是因为 `FunctionEmitter._nextReg` **只增不减**，
  内联写法很快耗尽 242 个字节码寄存器（见 §3.12）。

**字段顺序**：`TypeMapper` 生成的 IR 结构体字段按字母序（`StringComparer.Ordinal`），
helper 递归使用 `StructType.Body.ElementTypes` 的同一顺序，`GEP` 偏移与 IR 布局一致。

**验收**：

- `f5_acceptance.st`：`run` 输出 `1 / 0 / 0 / 1`、退出码 `0`；去掉 `Print` 的版本
  `verify` 0 条诊断、退出码 `0`（含 `Print` 的版本会因 C7 报 `E2006`，与本项无关）；
- `IronST.Frontend.Tests/StructComparisonTests.cs`：**17 例**
  （成功：同类型 `=`/`<>`、嵌套字段、数组元素、数值/BOOL/REAL/枚举；
  拒绝：`<`/`>`/`<=`/`>=`、不同类型、结构体 vs 标量、`REFERENCE`/`STRING`/`WSTRING`
  （含嵌套/数组）、顶层数组、非左值、全局聚合）；
- `IronST.Integration.Tests/StructComparisonIntegrationTests.cs`：**6 例**
  （直接变量、嵌套 + 数组 + 多维数组、单字段/全 BOOL、结构体数组元素、
  嵌套字段操作数、三层嵌套）；
- 全量：**1907 通过 / 0 跳过 / 0 失败**；
- `CliTopLevelExceptionTests` 4 例仍通过：F5 修复后，改用仍会穿透到代码生成的
  聚合搬运限制作为异常边界触发源。

**已知边界（另行登记，不阻塞 A1 的局部结构体按值比较）**：

- **A8**：全局/外部聚合没有真实存储，字段读写会落到错误槽位；本轮前端拒绝比较；
- **A9**：`xs[0] := x` / `xs[1] := xs[0]` 的聚合搬运不完整；结构体数组需逐字段初始化；
- **C8**：`_nextReg` 只增不减；普通规模的长函数可能先撞寄存器上限；
- 首版不支持结构体字段中的 `REFERENCE` / `STRING` / `WSTRING`，会得到 `E2003`。

### 3.4 F9 —— typeId 无守卫，超限静默回绕（源码 + 运行时双证据）

分配链与超限行为：

### 3.7 F12 —— `CASE ... OF` 区间标签逐值展开 ⇒ `Off8` 分支越界

**观测**（独立探针 `S4_case_range.st` / `S4b_case_small.st`，`--libs host`）：

| 用例 | 结果 |
| --- | --- |
| `temperature := 75;` + `0..50 / 51..80 / 81..200`（跨度 200） | ❌ `System.InvalidOperationException`：`Branch offset 2005 out of range for 8-bit patch (label '__Main_bb1': offset=45, target PC=2051); allowed range is -128..127.`（`BytecodeAssembler.ApplyPatches`） |
| 对照 `0..1 / 2..3`（小跨度） | ✅ 正常停机，命中正确分支 |

**根因（源码实证）**：

1. `IronST.LLVMCodeGen/CodeGen/StatementEmitter.cs:331-333`：区间标签被**逐值展开**为
   多个 `switch` case（`for (v = RangeStart; v <= RangeEnd; v++) switchInst.AddCase(v)`）。
2. `IronST.BytecodeGen/FunctionEmitter.cs` `EmitSwitch`（`:1246-1253`）：switch 被降为
   **逐 case 的 `BEQ` 线性链**。

跨度 200 ⇒ 约 200 条 `BEQ` ⇒ 分支目标距离 > 127，超出 `Off8`（8-bit 相对跳转）范围。

**与 F2 的关系**：F2 `583ff66` 把 `Off8` 越界从「`(sbyte)` 静默回绕」改为**抛异常**，
故历史自述的**「死循环」表现消失**（回绕到错误目标 → 现为显式异常）；但同一构造**仍不可用**。

> **边界（不得扩大宣称）**：本项**只**针对 `CASE` **区间标签**的逐值展开问题。
> 「大量**单值** `case` 是否同样越界」「是否应改一般 switch 编码 / 引入长条件分支」**未取证、未登记**，
> 须独立范围裁定。修复**不得**触碰字节码头部、ISA、VM，或 F2 的 8-bit 越界守卫。

**修复与验收（`b69046c`）**：

- **修复**：`IronST.LLVMCodeGen/CodeGen/StatementEmitter.cs` `EmitCase` —— 区间标签改用
  **范围判定** `lo <= x <= hi`（`icmp sge`/`icmp sle` + `and`，同一分支内多区间再 `or`，
  每个含区间的分支一个条件块、按源码分支顺序判定，末者 else → `default`），**不再逐值展开**；
  单值 / 枚举标签仍走 `switch`，`FunctionEmitter.EmitSwitch` 的编码策略**原样保留**。
- **修复前基线（`e99bb1f`，只读）**：`IronST.BytecodeGen.Tests/CaseRangeTests.cs` **20 例 →
  15 失败 / 5 通过**；失败集中于**大区间**（`0..50 / 51..80 / 81..200`，跨度 200，
  `Branch offset 2005 out of range … allowed -128..127`）与**区间与单值标签共存**
  （`offset 135`）；失败均发生在**编译期**（`BytecodeAssembler.ApplyPatches`）。小区间对照通过。
- **修复后**：同 20 例 **20/20 通过**（含边界值 `0/50/51/75/80/81/200/201/-1`、未匹配值走 ELSE、
  区间与单值共存、逗号分隔多单值）。
- **无区间标签场景**：区间分支数为 0 时完全走旧路径 —— 实测对照 `e99bb1f`，
  IR 与反汇编**逐字节一致**（探针 `S4c`：`157 bytes` 不变）。
- **字节码差异**（对照 `e99bb1f`）：小区间（`0..1 / 2..3`）`142 → 198 bytes`（范围判定比少量
  展开 case 略大）；大区间（跨 200）旧为**构造失败** → 现 `261 bytes`、正确命中 `51..80`。
- **F2 守卫保留**：`583ff66` 的 `Off8` 8-bit 越界守卫**未改**，仍在写侧拦截。
- **本切片边界（不得扩大宣称）**：仅覆盖 `CASE` **区间标签**；**不覆盖**「极大量**单值** `case`
  仍可能触达 `Off8` 上限」的潜在溢出 —— 该情形未取证、未登记，仍属独立范围裁定。

#### 3.8.1 验收（2026-10-22）—— 注入路径可用 + 内置 VM 无数学函数

### 3.9 ⑥ —— 实数 ↔ 整数 跨界转换缺失（2026-10-22 端到端实测）

**登记订正**：原登记「`INT` 与 `REAL` 混合运算结果标签错成 INT」指向**类型标签**。
端到端探针实测表明：**标签只是表象**，真实缺陷是**值转换缺失**，且发生在**两处**。
按原描述修会漏掉赋值侧。

**实测矩阵**（6 例端到端：ST → `FrontendPipeline` → `IRGenerator` → `ByteCodeGenerator` → VM）：

| 构造 | 结果 |
| --- | :--: |
| `avg := sum / 2.0`（`sum: INT` · `avg: REAL`，期望 `27.5`） | ❌ **值错** |
| `d := r`（`d: DINT` · `r: REAL`，期望 `55`） | ❌ **值错** |
| `d := i`（`d: DINT` · `i: INT` 宽化） | ✅ |
| `i := d`（`i: INT` · `d: DINT` 窄化） | ✅ |
| `lr := r`（`lr: LREAL` · `r: REAL`） | ✅（靠运行时 tag 兜底，精度会掉） |
| `r := 1.5`（`REAL` 字面量） | ✅ |

**边界**：整数内部、实数内部的路径**都正确**；缺陷**只在「整数 ↔ 实数」这个边界上**。

**IR 证据**（`sum: INT` · `avg: REAL` · `sum := 55; avg := sum / 2.0`）：

```llvm
%sum = alloca i16, align 2
%avg = alloca float, align 4
store i32 55, ptr %sum          ; ③ 整数字面量未按目标槽宽度截断
%sum.ld = load i16, ptr %sum
%fdiv = fdiv i16 %sum.ld, 2     ; ① 左操作数未 SIToFP，结果类型退化为 i16
store i16 %fdiv, ptr %avg       ; ② store 不按目标变量类型转换
```

对照纯 `REAL` 路径（`a: REAL; b: REAL; c := a / b`）⇒ `fdiv float` / `store float`，
**类型完全正确** —— 源/目标恰好都是 `float`，把同一处缺口掩盖了。

**两处根因**：

1. **运算侧** —— `ExpressionEmitter.EmitBinaryExpr` 实数分支缺整数操作数提升。
   同文件的 `EmitIntPower` **有**该转换（`CastInst.CreateSIToFP`），**实数分支漏了**。
2. **赋值侧** —— 实数赋给整数未做截断/转换。

**为何不是内存破坏**：VM 槽是**统一 64 位**（`stack[addr] = R[reg]`，运行时 tag 保留），
IR 里的位宽只是**建议值** ⇒ 位宽不匹配（如 `store i32 55` 写进 `alloca i16`）
**不会越界写**，只影响值语义。这解释了为何整数宽化 / 窄化两例都通过。

**`EnsureType` 已具备所需能力，缺的只是调用点**：`ExpressionEmitter.EnsureType`（`:655`）
**已实现全部所需转换** —— 整数↔整数位宽（`SExt`/`ZExt`/`Trunc`）、整数→实数
（`SIToFP`/`UIToFP`）、实数→整数（`FPToSI`/`FPToUI`）、实数↔实数位宽（`FPExt`/`FPTrunc`）。
但它的调用点只有三处：`MathFunctions`（数学内建）、`TypeConversionFunctions`
（显式转换函数 `INT(x)`/`REAL(x)`）、`StatementEmitter` 的 FOR 计数器
—— **赋值与实数运算两条主路径都不调它**。

⇒ **修法因此收窄**：不需要新写转换helper，只需在这两条主路径上补 `EnsureType` 调用。

**IR 层缺自洽校验**：`fdiv i16 %sum.ld, 2` 这种**操作数类型不一致**的 IR 被正常产出、
一路流到后端，**全程无断言拦截**。补一条「二元运算两操作数类型必须相同」的校验，
此类缺陷会当场暴露，而不是靠端到端撞出来。

> **边界（不得扩大宣称）**：探针只覆盖上表 6 条路径。函数返回值、数组元素赋值、
> 比较运算、`FOR` 边界等**未穷举**；修完后需新增端到端断言作回归保护。

#### 3.9.1 ⑥ 修复记录（2026-10-22）

按 §3.9 收窄后的结论 —— **不新写转换 helper**，只在三条主路径上补 `EnsureType` 调用：

| 路径 | 改动 | 文件 |
| --- | --- | --- |
| 运算侧 | `ExpressionEmitter.PromoteToReal` —— 实数分支的**两侧**操作数都提升为结果实数类型（`SIToFP` / `UIToFP`） | `ExpressionEmitter.cs` |
| 赋值侧 | `ExpressionEmitter.ConvertToTargetType` + `StatementEmitter.EmitAssignment` —— 赋值右值按**目标变量类型**转换（实数→整数走 `FPToSI` / `FPToUI`，向零取整） | `ExpressionEmitter.cs` / `StatementEmitter.cs` |

### 3.10 A8 —— 全局/外部聚合没有真实存储（2026-10-23 新发现）

**探针**（`f5_global.st`）：

```iecst
TYPE P : STRUCT a : DINT; b : BOOL; END_STRUCT; END_TYPE;

PROGRAM Main
VAR_GLOBAL
    x : P;
    y : P;
END_VAR
VAR
    ok : BOOL;
END_VAR
x.a := 1;
x.b := TRUE;
y := x;
ok := x = y;
END_PROGRAM
```

**实测**：

- 修复前 `x = y` 在代码生成/运行期触发 `SlotOverflow`：全局槽只登记了聚合变量
  本身，字段展开没有对应的全局存储映射；
- `x.a := 1` 的字段地址基址来自 `EnsureReg(GlobalVariable)` 的**回退分支**，
  该寄存器未初始化，`STORE` 会写进错误的 VM 槽；
- 读回 `x.a` 可能“碰巧”等于 1，但这不代表落到了正确的全局槽；跨 POU 访问或
  比较时会暴露为错值 / `SlotOverflow`。

**当时处置**：`CheckStructComparison.IsGlobalStructOperand` 在前端拒绝

### 3.11 A9 —— 聚合整体写入/读出数组元素不完整（2026-10-23 新发现）

**探针 1**（`f5_copy.st`，源/目标为数组元素）：

**探针 2**（`f5_boundary3.st`，嵌套结构体数组元素之间整体赋值）：

```iecst

    xs : ARRAY[0..1] OF P;
```

```text
错误: IronST 内部错误（这属于工具缺陷，不是你的程序的问题）

```

**根因**：聚合 load 只接受 alloca 作为源；数组元素地址是 `GEP`，没有对应的

### 3.13 A10 —— 未赋值 `REAL` 的 `<>` / 排序比较（2026-10-23 新发现）

**探针**（`voidreal.st` / `voidreal2.st`）：

```iecst
PROGRAM Main
VAR r : REAL; b : BOOL; END_VAR
    b := r <> 1.0;   (* 实测：TypeError: Cannot compare Void and Float64 *)
    b := r = 1.0;    (* 实测：0，不报错 *)
END_PROGRAM
```

**根因**：局部变量未赋值时槽位是 `Void`（VM 默认值），而不是 IEC 要求的类型零值。
`=` 走 `FEQ`（只读 `FloatValue`，`Void` 视为 0），`<>` / `<` / `>` 走 `CMP` →
`BcValue.Compare`，后者对含 `Void` 的换标签比较直接抛 `TypeError`。

**影响**：任何未显式赋值的 `REAL` 参与 `<>` / 排序比较都会中断程序；
与“变量按类型零值初始化”的 IEC 语义相惖。

**建议验收**：未赋值数值槽按类型零值参与运算/比较（或显式诊断）；
`REAL` 的六种比较在 `Void` 下行为一致。**本轮未修**（不在 A8/A9 范围内）。

### 13.1 MOD-HCALL —— 证据与定位（2026-10-21 已修复；以下保留取证历史）

- **最小复现**（端到端 `Frontend → IRGen → ByteCodeGen → VM`，宿主仅注册 `Print`）：
  ```
  PROGRAM Main
  VAR x : INT; END_VAR
      x := 7 MOD 3;
      Print(x);
  END_PROGRAM
  ```
- **端到端结果**：**前端 OK / 编译通过**；运行时
  `RuntimeErrorException: [IllegalOpcode] at 0x22: HCALL 49: unregistered`（`49 = 0x31 = MATH_IMOD`）。
  对照 `7 / 2`（`IDIV` 直接指令）**开箱可用**，`Print → 3`。
- **当前定位**（源码实证）：
  1. `FunctionEmitter.EmitBinaryOperator` 把 `SRem`/`URem` 交给 `EmitMathHcall(HC_MATH_IMOD)`（`FunctionEmitter.cs:737/:740`）；
     `HC_MATH_IMOD` 为**硬编码静态 ID** `0x31`（`:86`），发射 `MOV A0 / MOV A1 / HCALL 0x31 / MOV dst,A0`（`:790-803`）。
  2. 该路径**不进 `HostIdx` 重定位表**（静态 ABI ID，`RecordHostRef` 不登记；`FunctionEmitter.cs:1837-1838`）。
  3. 消费侧 `VMBase.RunLoop` 查 `host.TryInvoke(0x31)` 未命中 ⇒ 抛**带诊断的 `RuntimeError`**（不崩溃）。
  4. **全仓 `MATH_IMOD`（`0x31`）handler 零注册**：CLI `DemoCommand`（注册 `Square`/`AbsVal`/`CSharpPrint`/`PrintPoint`）、
     CLI `ReplCommand`（仅注入 `IECStandardLibrary`，不注册任何 host）、IDE `DebugHostBridge`（仅 `PRINT_*`）、
     `Runtime.ConsoleApp`（`PRINT_*`/`READ_*`/自定义 `0x0100+`）**均无**。

**修复（2026-10-21）**

- 新增 `IronST.Runtime.Shared/MathStandardLibrary.cs`：
  - `SRem` 走 `MATH_IMOD = 0x31`，按 C# `%` / LLVM `srem`，余数符号跟随被除数；
  - `URem` 不再复用 `0x31`，改用新增的 `MATH_UMOD = 0x0039`，按 `ulong` 位模式取余；
  - 除零抛 `RuntimeErrorException(RuntimeErrorType.DivideByZero, 0, "Divide by zero")`。
- `VMBase` 构造时通过 `MathStandardLibrary.Register` 安装默认 handler；
  `HostBridge.RegisterIfAbsent` 保证宿主已显式注册的同 ID 实现优先。
- `FunctionEmitter` 的 `HC_MATH_IMOD` / `HC_MATH_UMOD` 改为引用 `HostCallIds`，
  避免两处常量漂移；`SRem` / `URem` 分别发射不同 ID。
- 回归覆盖：`ModIntegrationTests`（ST 正/负数、除零）、
  `ModuleMetadataIntegrationTests.Invoker_IntegerMod_UsesBuiltinMathHandler`
  （`.stmod` 按名调用）、`VMArithmeticTests`（IMOD/UMOD/除零）。

- **历史未决项（已裁定）**：
  - 期望的**整数 `MOD` 语义**（含 `MOD` 对**负数**、**除零**、各整数宽度的行为）；
  - **符号映射**：`SRem`（有符号）与 `URem`（无符号）当前**共用同一 `0x31`**，是否需要区分；
  - **运行时装配位置**：`MOD` 应由**后端内建数值指令**提供，还是由**宿主 / 标准库桥**注册处理器
    （与 F13 方案丁的装配决策**相关但需独立裁定**）。
- **边界（不得扩大宣称）**：
  - 本证据仅覆盖 **`INT` 类型的 `7 MOD 3`** 一条；修复后的回归覆盖有符号正/负数与除零，
    **未穷举**所有整数类型、位宽边界和 `URem` 的全部位模式。
  - **未取证**其它静态 ID 路径（`MATH_FMOD`/`MATH_FPOW` 常量已声明但**实际未发射**）是否存在同类现象；
    F13 浮点标准库仍不在本次修复范围。
  - 本条已修复并纳入独立回归；**不得**据此宣称 F13 已放行。
