## 2. 重定位

### 2.1 模块内补丁：只有两种 ［事实］

`IronST.Runtime.Shared/BytecodeAssembler.cs:24-30`：

```csharp
private enum PatchKind { Addr32, Off8 }
private readonly record struct PatchEntry(int Offset, string Target, PatchKind Kind);
```

- **`Addr32`** —— `Jmp`/`CallFunc` 的 32 位绝对目标 PC
  （`:71-77`、`:183-193`），`ApplyPatches()` 里 `PatchUInt32(offset, (uint)targetPC)`（`:497-499`）。
- **`Off8`** —— 条件跳转的 8 位有符号相对偏移（`:90-149` 七处），
  `rel = targetPC - (offset + 1)`，越界抛 `InvalidOperationException`（`:500-513`，F2）。
- `ResolveLabel`（`:536-543`）：先查标签，再查函数表，都没有则抛
  `Undefined label or function`。

**关键结论 ［事实］**：`ApplyPatches()` 在 `Build()` / `SaveTo()` / `BuildModule()`
（`:518-534`）里就被调用 —— **磁盘产物里不含任何重定位记录，一切已经烧死**。
所以增量中间产物（「元数据 + 汇编代码」）是**新增格式**，不是现有 `.irst` 的扩展。

### 2.2 六类跨模块重定位 ［冻结 · 已确认］

> **分类口径：按补丁种类划分** —— 与 `BytecodeAssembler.PatchKind` 对齐并扩展到跨模块。
> 另一版口径（按「链接器重写载体」划分、以调试段替换 Off8）**已否决**。
> 调试段偏移不单独成类，随所属指令重定位一并处理。

| # | 重定位对象 | 现状编码 | 链接器何时必须处理 | 证据 |
| --- | --- | --- | --- | --- |
| 1 | 调用 / 跳转目标 | `Addr32`，32 位绝对 PC | **总是** —— 绝对 PC 经任何平移即失效 | `BytecodeAssembler.cs:71-77,183-193,497-499` |
| 2 | 条件跳转相对偏移 | `Off8`，8 位有符号 | **仅跨模块分支** —— 模块内天然稳定（见 2.3） | `:90-149,500-513` |
| 3 | 全局变量槽位 | `GETG` / `SETG` 的 16 位槽位立即数 | **总是** —— 合并全局表必然重排 | `:228-238` |
| 4 | 常量池索引 | `LDC` 携带的池索引 | **总是** —— 合并常量池必然重排 | `:548-550` |
| 5 | 结构体类型 ID | `StructRegistrations (byte typeId, int fieldCount)` | **总是** —— 合并类型表必然重排 | `ByteCodeGenerator.cs:155` |
| 6 | 宿主函数 ID | `HCALL` 的 `ushort` | 依外部库解析结果 | `Enums.cs:166`、`DebugHostBridge.cs:38` |

**第 2 类为何仍进清单**：模块内分支在拼接下稳定，但**跨模块**分支的相对位移取决于
最终布局；且 8 位相对偏移跨模块很可能根本不够 —— 届时只能改绝对跳转或插入跳板，
**那是指令集层面的改动，必须同步递增指令集版本**（第 1.2 节）。

### 2.3 拼接稳定性推论 ［事实 + 推论］

- **`Off8` 模块内稳定**：`rel = targetPC - (offset + 1)`，源与目标同时平移同一常数，
  差值不变 —— **只要分支不出模块，拼接后无需回填**。这是 2.2 中第 2 类的处置前提。
- **`Off8` 跨模块不稳定**：目标在另一模块时，相对位移完全取决于两模块的最终相对位置。
- **`Addr32` 全部失效**：绝对 PC 在任何平移后都错。
- **`GETG`/`SETG` 槽位、常量池索引、结构体类型 ID 全部失效**（见 2.4）。

### 2.4 全局槽位是 eager 解析 —— 链接器的头号障碍 ［事实］

`BytecodeAssembler.cs:228-238`：

```csharp
public BytecodeAssembler GetGlobal(byte rd, string name)
{
    _b.GETG(rd, _globalNames[name]);   // ← 发射瞬间就把 short 烘进指令
    return this;
}
```

- `_globalNames`（`:37`）是 `Dictionary<string, short>`，**没有走 `_pendingPatches`**。
- 未声明即访问 → `KeyNotFoundException`（不是友好诊断）。
- 合并多个模块的全局表时，槽位必然重排 → **已发出的 `GETG`/`SETG` 操作数全部作废**，
  而当前产物里没有任何记录能告诉链接器「哪些偏移是槽位」。

> **推论**：要么给中间产物补槽位重定位记录，要么把 `GetGlobal`/`SetGlobal`
> 改成像标签那样走待回填通道。两者都属于阶段 0B 的接口改动。

## 5. 字段布局不重定位 ［冻结 + 事实］

**决定**：结构体字段偏移在编译期确定，链接器**不重定位**字段布局。

**成立前提（源码证据）** `IronST.LLVMCodeGen/TypeMapping/TypeMapper.cs:146-153`：

```csharp
private static List<KeyValuePair<string, IECType>> GetSortedFields(IECType structType)
{
    // TODO: Frontend 的 Dictionary<string, IECType> 不保证源码顺序。
    // 按字母序排列作为确定性回退。若 Frontend 改为有序字典，可直接迭代。
    return structType.Fields!
        .OrderBy(f => f.Key, StringComparer.Ordinal)
        .ToList();
}
```

- 布局由**字段名的 `Ordinal` 排序**唯一决定 —— 与声明顺序无关，所以跨模块可复算，
  不需要重定位。
- ⚠️ **`Ordinal` 排序对大小写敏感**（`'Z'` = 90 < `'a'` = 97）。
- ⚠️ **那条 TODO 是潜在地雷**：一旦有人把 `Fields` 换成有序字典（按源码顺序），
  布局会静默改变，而跨模块按旧序复算的对端仍用旧布局。

**连带要求**：接口摘要（序列化的 `ExternalLibrary`）**必须保留字段名原始大小写**。
`ExternalLibrary.cs:40` `Fields` 是 `List<(string Name, string TypeName)>`，
`SemanticAnalyzer.cs:174-178` 用 `f.Name` 原样作键（比较器才 `OrdinalIgnoreCase`），
**键本身未被折叠** —— 序列化时同样不得折叠。
