#### 1.4.3 单一根因 `[关键]`

**根因是一个判据漏了 `StructType`。** `FunctionEmitter.cs:1369-1370`：

```csharp
private bool IsScalarAlloca(Value ptr) =>
    ptr is AllocaInst ai && ai.AllocatedType is not ArrayType && !_structAllocas.Contains(ptr);
```

- 只排除 `ArrayType`（`Instruction.cs:137`），**未排除 `StructType`（`:185`）**；
- `!_structAllocas.Contains(ptr)` **恒为 true**（§1.2：零写入点）。

⇒ 结构体 alloca 被误判为"标量 alloca"，于是聚合整体 load/store 落到单槽路径：

| IR（正确） | 字节码路径 | 实际效果 |
| --- | --- | --- |
| `load %Point, ptr %p` | `GETL` 单槽 `FunctionEmitter.cs:916-918` | 只读 4 字节 = field 0 |
| `store %Point, ptr %q` | `SETL` 单槽 `FunctionEmitter.cs:963-965` | 只写 4 字节 = field 0 |
| `store [2 x i16]`（数组） | `SETR` 单槽 `FunctionEmitter.cs:968-970` | 只搬第一个元素 |

`q := p` / 结构体参数因此**只搬运第一个字段**；单字段结构体恰好只有 field 0，
故 `c3` / `pm2` 的"通过"是**边界巧合**，不是支持（`FunctionEmitter.cs:1369` 的判据面前，
单字段与多字段走同一条错路，只是错得不明显）。

**FB 同源**：FB 实例在 IR 层是 `%FB1 = type { i16 }` + `define void @FB1(ptr %__instance)`
（`FunctionCodeGenTests.cs:130`、`:159` 断言过 IR 形态），`fb3.ll` 实测取证显示
`call void @FB1(ptr %fb)` 与体内 `store i32 42, ptr %v.addr` **完全正确**。
`EmitAlloca`（`FunctionEmitter.cs:888-894`）把**栈槽号**装进寄存器当"结构体值"，
而 `CALL` 之前没有把实例地址放进约定寄存器 ⇒ FB 体内的 `store` 写回**错误位置**，
Main 读 `fb.v` 拿到旧值。IR 对、字节码错。

> **⚠️ 后端根因 ≠ 语义归属（2026-10-15 裁定）**：
> 「`EmitAlloca` 把结构体值当槽号、`CALL` 前不传实例地址」是**源码可证的实现缺陷**，
> 与语言语义无关，作为**独立实现缺陷继续追踪**；
> 但「FB 成员赋值**是否必须**对调用方可见」是**语言语义问题**，当前规范证据不足 ⇒
> `fb3` 的期望结果标记为**待定** —— **不得以当前不可见行为反推"不要求可见"**，
> 也不得仅凭测试期望宣布"必须可见"。语义裁定前 `fb3` 只作诊断用例，
> 不单独决定架构方向（§6.3.5）。

> **⚠️ 这不是"Arena 没接上"，而是"聚合类型整体搬运从未实现"**：
> 后端只有"按标量槽"（`GETL`/`SETL`）和"按 GEP 偏移"（`GETR`/`SETR`）两种能力，
> **没有"按 `sizeof(aggregate)` 的块搬运"**。§1.4.2 的 #1/#2/#10 之所以能用，
> 正是因为它们**只**用到那两种既有能力。

### 2.2 `SYM-1` 命名空间语义与大小写 —— 方案 C + 一元语义 `[已冻结]`

**冻结（2026-10-15 评审裁定）**：

1. **D2 选 C**：保留原始名称（用于诊断、调试信息、接口序列化），
   符号**解析键**使用统一的规范化形式（大小写不敏感）。
2. **D1 采用前端的一元命名空间语义**：函数、全局变量、类型在语言层面不允许同名。

**不选 A（全链 `OrdinalIgnoreCase`）的理由**：涉及宿主注册表 `:87/:139`、IR SourceMap
`IRSourceMapParser.cs:32`、LSP 文档/缓存与查询（契约 §4 后四行）等多层行为，改动面过大。

**不选 B（全链 `Ordinal`）的理由**：会改变语言**已接受**的标识符语义
（`Main` 与 `main` 今天在前端是同一个 POU），还必须额外修补重复声明判定，等于改语言。

**C 的四条具体契约 `[已冻结]`**：

| # | 要求 |
| --- | --- |
| SYM-1.a | 原始名称保留，用于诊断、调试信息与接口序列化 |
| SYM-1.b | 解析键 = 统一、明确规定、**不依赖当前区域设置**的大小写不敏感规范化规则 |
| SYM-1.c | 同一编译单元与跨模块链接采用**完全相同**的冲突规则；<br>**类型、POU、全局变量的冲突规则在编译期与链接期必须一致** |
| SYM-1.d | 链接器必须**跨表**检查标签 / 函数 / 全局变量之间的冲突，<br>**不得**继续依赖表的独立性或 `ResolveLabel` 的查找优先级 |

#### `SYM-1.e` 规范化键必须有唯一生成入口 `[已冻结]`

**不得在各层分别调用 `ToUpper()` / `ToLower()`。** 必须抽出**唯一的符号键生成入口**，
统一用于以下四处，保证同一符号在全链得到同一个键：

1. 声明冲突检测；
2. 引用解析；
3. 接口摘要匹配；
4. 跨模块符号合并。

**验收用例（键入口的行为必须被直接验证）**：

| 用例 | 期望 |
| --- | --- |
| `Main` 与 `main` | 生成**同一个键** |
| 不同区域设置（如土耳其语 `i`/`I`）下 | 键**完全相同**，不随 `CurrentCulture` 变化 |
| 标签与函数同名 | 键相同 ⇒ 冲突**必须**被检出（不得靠查找优先级放过） |

#### `SYM-1.f` 宿主函数名与语言符号规则分开 `[已冻结]`

宿主 ABI 的**名称 ↔ ID 映射必须稳定**：
**不得**因为前端符号规范化规则改变，就悄悄变更已发布的宿主调用约定。
宿主命名规则的变更属 **ABI 变更**，须走 ABI 评审，不随 `SYM-1.b` 自动跟随。

### 2.3 `SYM-2` 规范化键 ≠ 合并数据结构（边界）`[已冻结]`

**必须写进文档的边界**：采用规范化键，**不代表**要把所有内部字典合并成一张表。

- 内部数据结构可以继续分开（标签表、函数表、全局表各有用途）。
- 必须统一的是**符号身份的定义**与**冲突检测规则**，不是存储结构。
- 各表可以各自保留 `Ordinal` 存储，只要**比较/查找/去重**一律走规范化键。

## 3. 重定位表设计

### 3.1 记录模型 `[要求已冻结；字段布局随格式方案]`

重定位记录**不能只有「类型 + 数值」**（否则 §1.3 的引用点无法还原）。每条记录至少含：

| # | 字段 | 用途 |
| --- | --- | --- |
| 1 | 重定位类型 | 六类之一 |
| 2 | 所属代码段或数据段 | 确定被改写对象 |
| 3 | 段内偏移 | 指向需要回填的字节位置 |
| 4 | 原始符号名或索引来源 | 解析跨模块引用 |
| 5 | **引用源位置** | 文件、行列或可稳定关联的源位置 ID —— **未定义符号诊断的前提** |
| 6 | 编码宽度与规则 | 写入前校验，防止静默截断 |
| 7 | 加数或相对基准 | 仅对相应重定位类型使用 |

### 3.2 宽度与容量必须分开定义 `[原则]`

**编码宽度 ≠ 允许的目标值容量。** 例：`Addr32` 编码 32 位，**不代表**允许生成接近 4 GiB 的代码段；
实际代码段上限仍是模块格式的 **16 MiB**（`BytecodeModule.cs:63`）。

### 3.4 三类"跨模块必然重排" `[事实]`

| 类 | 为何必然 | 定位 |
| --- | --- | --- |
| `REL-1` | 各模块 PC 都从 0 起，拼接后全部失效 | `_labelDefs` 存的是模块内 PC（`:21`、`:100`） |
| `REL-3` | 各模块 `_globalCount` 初值 0，槽位从 0 起 | `DeclareGlobal`（`:246`） |
| `REL-4` | 各模块 `_constPool` 初值为空，常量索引都从 0 起 | `AddConst` / `AddString` 返回 `Count-1`（`BytecodeBuilder.cs:62-79`） |
| `REL-5` | **`Generate()` 每次把 `_nextStructTypeId` 重置为 1** ⇒ N 个模块各自从 1 开始，**ID 重叠是常态而非边缘情况** | `ByteCodeGenerator.cs:50` |

> 由此，§6 的"同 ID 不同布局冲突"**不是只有溢出才会发生——链接两个模块必然发生**，
> 今天不炸只因生产侧已死（§1.2）。`REL-5` 的重编号是**多模块链接的常规步骤**，不是防御性编程。

### 3.6 切片 2/3/4 期间核实的事实 `[事实]`

1. **`GlobalIdx` 的生产发射路径不是汇编器的命名 API。** `GetGlobal` / `SetGlobal`

   直接发射 `DebugInstr.Slot(OpCode.GETG/SETG, …)`（`FunctionEmitter.cs:904`、`:958`），

   故按声明名回填是安全的。

   汇编器 `_globalNames` 用默认 `Ordinal`（`BytecodeAssembler.cs:68`）。属 `SYM-1` 范畴，

4. **引用源位置取决于 IR 源映射**：`IRGenerator` 默认 `NullDebugEmitter`（`IRGenerator.cs:15-17`），

   `BuildSourceMap`（`DebugViewModel.cs:554-561`）时记录带文件名与行号。两条路径均有测试。
   > `[2026-10-19 订正]` CLI 路径已同样挂 `IRDebugEmitter`（`IronRuntime.Compile` 受
   > `emitDebugInfo` 控制，`CompileFiles` 恒挂）⇒ `SourceMap` 非空，运行期报错带
   > `文件:行号`。“CLI 记录为 `Unknown`”不再成立。

   > `VMOptions.SourceLocator`（构造见 `SourceResolver.FromMap`），VM 在错误边界

   > 或旁车缺失时仍只报 PC。
5. **`VAR_GLOBAL` 只能嵌套在 `PROGRAM` / `FUNCTION` 体内**：置于顶层报 `E1001`
   （期望 `EOF` / `PROGRAM` / `FUNCTION` / `FUNCTION_BLOCK` / `CONFIGURATION`），
   与 `ReferenceEndToEndTests.cs:9-11` 的既有说明一致。
6. **`IronST.LLVMCodeGen/Debug/` 会被 ripgrep 按 `Debug/` 忽略规则跳过**，但 git 正常跟踪
   （`git ls-files` 列出 `IDebugEmitter.cs` / `IRDebugEmitter.cs` / `NullDebugEmitter.cs`）。
   检索该目录须用文件系统遍历，**勿据检索空结果判定"类不存在"**。
7. **`ConstIdx` 与 `GlobalIdx` 的关键区别在"身份从哪来"**：全局变量有声明名可解析，
   常量没有。故 `ApplyGlobalIdx` 查 `_globalNames`，而 `ApplyConstIdx` 只能靠显式钩子
   `ConstIndexRemap`（`BytecodeAssembler.cs:61`，默认 `null` = 恒等映射）。`Validate` 进一步

   模块局部索引误当跨模块身份，链接期会解析到错误目标。
8. **常量池只追加不去重**：`AddConst(long)` / `AddConst(double)` / `AddString(string)`
   （`BytecodeBuilder.cs:62` / `:69` / `:76`）返回 `Count-1`，重复字面量必得新索引。这与
   §3.3 `REL-4` 冻结的"首版追加合并、不去重"一致，且使"索引一经分配终身不变"成立，
   回填按索引回查才安全。
9. **`ConstIdx` 的容量上限依据运行时消费逻辑，不是字段类型**：`LDC` 编码为有符号 LE32，
   若只看编码可表示负值；但 VM 拿它直接当 CLR 数组下标且**无预检**
   （`VMBase.RunLoop.cs:71`），负数必然越界。故上限取 `Array.MaxLength - 1`
   （`RelocationRules.MaxConstIndex`，`Relocation.cs:98`），**用符号引用而非写死数字**：
   该值随运行时而非本仓库决定，写死会把"未经核实的容量"变成看似冻结的事实（§8.6-2）。
10. **并非所有 `LDC` 都有源行**：函数序言与地址建立期发出的常量不属于任何源行
    （`FunctionEmitter.cs:105` 显式清空 `_currentSrc`），记录**如实标 `Unknown`，不伪造**。
    端到端用例中这 8 条的值是 `0,0,1,1,2,2,3,3`。函数体内的字面量在 IDE 路径下正常带出
    文件名与行号。"有无源信息"的判据复用 `DebugModule.cs:65` 的既有规则
    （`SrcFile != null && SrcLine > 0`，见 `SourceOf`，`FunctionEmitter.cs:1338`），**不另立规则**
    ——两处判据若分叉，会出现"源映射有行、重定位记录没有"的不一致。
11. **`EmitLdc` 的 `source` 参数刻意不给默认值**（`BytecodeAssembler.cs:345`）：
    `RelocationSourceLocation` 是结构体，`default` 会给出行 **0**，而 0 是合法行号，会被误当成
    真实源位置。无源时须显式传 `RelocationSourceLocation.Unknown`。
12. **新增 `BytecodeBuilder.PatchInt32`**（`:108`，小端）：与 `LE32`（发射路径）字节序一致，

    字节等价；保留符号语义供后续有符号 32 位立即数复用。
13. **`HCALL` 编码与 `GETG/SETG` 不同构**：`HCALL` = 操作码 + 2 字节、**无 rd 字节**，

14. **生产发射路径实为三条，非原记的"唯一写入点"**：用户宿主调用（`FunctionEmitter.cs:1127`）、

    原记写入点 `:1096` 已随切片 2–4 漂移至 `:1127`；另有指令重放路径 `:301-302` 非生产。
15. **两套 name→ID 机制互不一致（登记为 `HOST-2`，本切片不修）**：CLI 走

16. **`HostCallIds` 与顺序分配器共用同一张按 ID 键控的派发表**（`HostBridge.cs:13`

### `HOST-1` 设计要求 `[已冻结]`

- 集中定义**数量上限 255（有效 ID `0..254`）**，**分配与写入两处都检查**，禁止截断 / 回绕；
  **在分配之前先检查总需求**，超限即诊断。
- **按宿主函数的稳定身份统一分配，不沿用各模块本地分配顺序** ——
  现码按注册顺序递增（`:173`），而 obj 产物一旦记录了 ID，**跨进程或注册顺序变化即失效**；
  这正是 `REL-6` 必须重编的依据。
- **`[边界]` 确定性排序只用于生成稳定结果，不是 ABI 身份本身。**
  不得把"按名称排序"当作宿主函数身份；跨模块统一编号必须保持
  **名称 ↔ 宿主调用契约的对应关系**，宿主函数身份由其 **ABI 定义**。

**重接生产路径时必须同时完成 5 项**：

1. 各模块**局部 ID → 全局链接 ID** 的映射；
2. 注册表中**相同局部 ID 对应不同布局**的合法重映射；
3. **同一最终 ID 对应不兼容布局时的硬错误**；
4. ID 容量边界测试：**255 个有效 ID 成功，第 256 个不同布局被拒绝**；
5. 端到端测试：链接后 `SNEW` 分配、字段访问、实例布局均正确。

> **关键顺序**：**先经链接器重编号，再检测最终 ID 的布局冲突。**
> 不能只在 `StructHeap.RegisterType` 里加"重复 ID 就报错"就认为解决 ——
> 局部 ID 在不同模块中重复**本来就是预期情况**（§3.4），那样会把正常链接误判成错误。

#### 6.3.1 Arena 必要性核验 `[结论：未发现必要性]`

逐一核验"Arena 为什么要存在"，只看**当前可达的消费需求**：

| Arena 组件 | 声称的作用 | 核验结果 |
| --- | --- | --- |
| `typeId`（`BcValue.SubTag`） | 运行时识别结构体类型 | 读取点仅 `BcValue.cs:318`（比较）、`:403`（`ToString`），两者都在 `Tag == Struct` **死分支**内（§1.2）⇒ **零可达消费** |
| `StructHeap.Alloc(typeId)` | 按 typeId 查 `fieldCount` 决定 arena 占用 | 唯一起点是 `SNEW`（`VMBase.RunLoop.cs:546`），而 `SNEW` 生产不发射（§1.2） |
| `SGET/SSET` + `fieldOffset` | 按偏移读写字段 | **不需要 typeId**：偏移是编译期常量（`DebugModule.cs:207`、`:209` 编码进 `Off8`），字段地址 = base + offset，扁平栈已能算（§1.4.2 覆盖 #1/#2） |
| `StructHeap.DeepCopy` | 结构体值拷贝 | 结构体整体赋值**必须**按值拷贝，但其实现位置在**字节码层**（§1.4.3），与 Arena 无关 |
| `StructHeap` 自身 | 结构体实例的堆存储 | 无任何语言语义要求堆分配（见 §6.3.2 候选条件表） |

⇒ **没有找到任何现有语言语义要求必须保留 `typeId` / `StructHeap` / `SGET/SSET`。**
> 不能因"已有死代码"就认定其有必要 —— 这是 2026-10-15 的明确裁定。

#### 6.3.2 分流条件核验 `[结论：暂不成立]`

"按场景分流"要求一个**可验证的触发条件**。候选条件逐一核验：

| 候选触发条件 | 来源 | 核验结果 |
| --- | --- | --- |
| 运行时按类型分支 / 比较 | ST 语法 | **无此语法**：`STRUCT` 字段名静态，无反射、无按类型 `CASE` |
| 动态字段访问 | ST 语法 | **无此语法** |
| 结构体需堆分配（生命周期超出词法作用域 / 体积过大） | 语义 | **当前无观测**：无全局变量声明入口（§1.4.2 观测口行）、无显式 new/delete、栈深上限未实测 |
| `REFERENCE TO` 指向结构体 | §1.4.2 覆盖 #10 | **已由通用指针路径支持**（`ev-ref` 通过），不需要 Arena |
| 结构体字段数 ≥ 2 | §1.4.3 缺陷 | **这是缺陷本身，不是语言语义** —— 见下 |

⇒ **找不到独立于缺陷本身的语言/运行时需求作触发条件。**
唯一"候选条件"就是 §1.4 观测到的几处**后端异常**，但**把异常当触发条件会混淆"修复"与"架构"**：
按字段数分流意味着"≥2 字段走 Arena、单字段走扁平栈"—— 这不是语言分界，是**实现缺陷的分界**。

> **⇒ 方案 ③（按场景分流）当前不可行**，除非先找到一个独立语言语义需求。

3. 后端层全通过 ⇒ "聚合整体搬运"已在扁平栈实现 ⇒ **无 Arena 必要性证据**

4. 语言层各项在语义裁定前**不得作为门槛**：`T-COV-1s`/`2s`/`3s` 与 `T-COV-4`
   的期望值待 §6.3.5 定案；**用未经确认的断言封死设计明确禁止。**

6. **在 (3) 成立之前，不得启动 ① 或 ③** —— 否则会把架构恢复或死代码清理，

#### 6.3.7 跨帧引用重定基：修复记录 `[已修复 2026-10-16 · 零 ISA / VM / Arena 改动]`

**结论 `[事实]`**：§6.3.6 登记的缺陷**已闭环**。后端在**不动 ISA、不动 VM、不动 Arena**
的前提下获得跨帧引用能力：`VAR_IN_OUT` / `VAR_OUTPUT` 的写穿透与
"调用返回后调用方可见"端到端可用。

**方案：调用点静态重定基（static per-call-site rebase）**

后端的「指针」是**创建它的帧**里的相对槽号（`GETR`/`SETR` 寻址 `addr = FP - 1 - slot`）。
`FRAME` 先把 `LR`、再把 `FP` 压栈（两槽），故

```
FP_被调方 = FP_调用方 - (调用方帧大小 + CALL 时已压栈槽数 + 2)
```

调用方在**传指针实参**时把槽号减去 `K = 帧大小 + stackArgs + 2`（**调用点编译期常数**），
被调方照常 `GETR`/`SETR` 即回落到调用方的同一槽：

```
FP_被调方 - 1 - (s - K) = FP_调用方 - 1 - s
```

逐层调用各自再减**自身**常数 ⇒ **自动复合**（`Outer → Inner` 两帧与 4 层递归均已实测）。

| 落点 | 内容 |
| --- | --- |
| `FunctionEmitter.cs` · `CrossFrameRebaseConstant` | `K = _nextSlot + stackArgs + 2`（`_nextSlot` 即 `FRAME` 操作数） |
| `FunctionEmitter.cs` · `RebasePointerReg` | 结果写**新**寄存器 —— `EnsureReg` 的缓存寄存器可能被同一实参复用（`f(v, v)`），原地减会二次扣减 |
| `EmitCall` 两处标量实参分支 | 帧上参数区压栈分支与 `A0–A3` 分支各重定基一次 |

指针实参只占 1 槽（`FlatSlotCount(Pointer) == 1`）⇒ 只经标量分支；聚合分支不受影响。

**边界**：

- **只改发射器**。`VMBase.RunLoop.cs` 的 `GETR`/`SETR` 语义、操作码表、`.isb` 头部
  **原样保留**（**无 ISA / 无版本变更**）；未恢复 Arena、未动 F7 / F9 / `StructTypeId` /
  宿主 ID。
- **FB 的 `__instance` 不改**：它是 FB 成员访问通道，其赋值可见性仍是语言层待裁定项
  （§6.3.5 首行）。故 FB 程序的字节码与本切片前**逐字节一致**，
  不得由本实现反推 FB 语义（`fb3` 预期仍**待定**）。
- **前提**：调用点 `SP` 恰为 `FP - _nextSlot - stackArgs`（`PUSH`/`POPN` 自平衡）。
  这与已验收的栈传参约定（`6f6774d`）是**同一个**假设。

**验证**：

| --- | --- |
| 新增端到端用例 `CrossFrameReferenceTests`（10 条） | 修前 **9 失败**（`ArrayBounds 999`）→ 修后 **10 通过** |

**取证时另观察到一处既有隐患（本次不修、不属本切片）**：

#### 6.3.8 跨基本块 `_valReg` 寄存器缓存：修复记录 `[已修复 2026-10-16 · 零 ISA / VM 改动 · 仅改发射器]`

**登记来源**：§6.3.7 末尾"取证时另观察到一处既有隐患"——当时**未修、未登记为缺陷**；
2026-10-16 由用户裁定**开独立切片**，与已验收基线 `585e88d`（跨帧重定基）**不混**。

**缺陷（后端层）`[事实]`**

`FunctionEmitter` 用 `_valReg` 把**可重物化**的值缓存进寄存器（`alloca` 基址 → `LDC` 槽号；
常量 → `LDC` / `LNIL`；参数 → `GETL` 参数槽）。该缓存**不在基本块边界失效**，
复用时不检查支配关系：

1. 调用返回后 `InvalidateRegistersAcrossCall` 丢弃这些条目；
2. 之后**首次使用**该值的位置决定它被物化在**哪一块** —— 若落在条件块 / 兄弟分支 /
   循环体内，寄存器就只在"该块被执行"的路径上被写入；
3. 沿**未执行该物化**的路径进入后续块时，直接复用该寄存器 ⇒ 读到**陈旧值**
   （干净 VM 的 `R8+` 初值为 `0`），并被当作**槽号 / 地址**使用 ⇒ **静默写错位置**
   （不越界、不报错）。

这与 §6.3.7 的"跨帧槽号基准不同"是**两回事**：这里是**同帧内寄存器生命周期**问题，
**无指针实参的程序同样出现**，且与 §6.2 Arena 方向**无关**。

**执行级复现 `[事实]`**（用户明确要求：仅凭寄存器编号 / 静态形状不足以断定，须确认真实执行路径）

最小形状：**前置一次调用** ⇒ 观测数组基址只在 `IF` 的 then 块内物化 ⇒ 条件为假 ⇒
合流块复用该寄存器。观测口仍用越界探测器，但把被破坏目标设为标量 `marker`
（声明在数组之前 ⇒ 占 slot 0）：陈旧基址 `0` 使 `g[0] := x` 的地址落到 `0`，
正好写进 `marker`，随后 `IF marker <> 7 THEN g[999] := 1` 即触发 `ArrayBounds`。

| 形状 | 执行结果 |
| --- | --- |
| 条件块内首次物化 + 合流块复用 | ❌ `ArrayBounds 999` |
| `IF` / `ELSE` 互补分支，else 侧复用 then 的寄存器 | ❌ `ArrayBounds 999`（该寄存器在 else 路径上**从未写入**） |
| 条件块物化 + 循环体复用 | ❌ `ArrayBounds 99` |
| **差分对照**：只把首次物化改为**无条件**（入口块），其余不变 | ✅ 无错 ⇒ 直接证明因果 |
| **反向对照**：回边重入（物化就在**本块**内） | ✅ 无错 ⇒ 回边复用本就不是危险面 |

**修复：基本块边界作废可重物化条目 `[已实现]`**

每进入一个基本块，丢弃所有**不是在「本块」或「入口块」里写进去的**可重物化条目：

| 判定 | 处理 | 依据 |
| --- | --- | --- |
| 物化于**本块** | 保留 | 块内物化指令先于其后的使用（顺序支配） |
| 物化于**入口块** | 保留 | 入口块支配函数内**所有**块（`BasicBlocks[0]`，由 `FrameBuilder.BuildPrologue` 最先追加）⇒ 任何路径上都已执行 |
| 物化于**其它块** | 丢弃 → 在当下块重新发射装载指令 | 物化点可能不在支配位置上 |

由此每个使用点的物化指令都落在**本块内、且在其之前**，**无需 CFG / 支配分析**
（`BasicBlock` 不提供后继接口，故不引支配树）。保留"入口块"一条是为了让绝大多数程序
（数组 / 结构体基址在 `alloca` 处、即入口块物化）**字节码逐字节不变**。

| 落点 | 内容 |
| --- | --- |
| `FunctionEmitter.cs` · `_valRegBlock` / `_currentBlock` / `_entryBlock` | 记下每个缓存条目**在哪个块里被写进寄存器** |
| `FunctionEmitter.cs` · `BindReg` | 收口全部 7 处 `_valReg` 写入点（含 `EmitAlloca`），一律登记块 |
| `FunctionEmitter.cs` · `InvalidateBlockLocalRegisters` | 块边界判据（本块 / 入口块保留，其余丢弃） |

#### 6.3.8.1 后续：调用边界 caller-saved + 跨调用活跃值 spill `[已修复 2026-10-21 · 无 ISA / VM / 格式变更]`

**缺陷**：字节码的 `R8+` 分配在每个函数内都从 `R8` 起算（§6.3.8 已记录物理重合），
调用方在 `CALL` 前装入寄存器的值，跨调用后仍被 `_valReg` 缓存复用；
被调方覆盖寄存器后，调用方读到的是被调方遗留值。

最小递归形状：

```st
FUNCTION Fact : DINT
VAR_INPUT n : DINT; END_VAR
    IF n <= 1 THEN Fact := 1;
    ELSE Fact := n * Fact(n - 1); END_IF
END_FUNCTION
```

`%n` 的 load 结果在 `CALL` 前物化进 `R17`；被调方也从 `R17` 起分配并覆盖它；
返回后 `IMUL` 读到 `2`，于是 `Fact(5)` 逐层得到 `2*1=2 → 2*2=4 → 2*4=8 → 2*8=16`。

**修复**：按 caller-saved 约定处理 `R8+`，并只对**跨调用仍活跃**的指令结果做 spill。

1. `FunctionLiveness` 做块级 SSA liveness（`use` / `def` 不动点，再反向扫描），
   对每个 `CALL` / 数学 `HCALL` 记录 live-after 的指令结果。
2. `FunctionEmitter.Analyze` 为这些不可重物化的结果分配稳定帧槽 `_spillSlots`，
   槽位紧跟在参数 / PHI / alloca / LR 槽之后，计入 `_nextSlot` 与 `FRAME`。
   槽号按**函数内指令顺序**分配，不依赖 `HashSet` 的枚举顺序，保证同一份源码的字节码稳定。
3. 在值的**定义处**发射 `SETL` 写回槽，而不是在调用点临时 `PUSH/POP`。
   因此槽在定义支配的所有路径上都有效，条件分支 / 合流无需路径敏感的 spill；
   也不改变 `SP`、栈参数布局和 `CrossFrameRebaseConstant` 的推导。
4. 调用边界 `InvalidateRegistersAcrossCall` 作废所有**可恢复**缓存：
   可重物化值重新发射装载；有 spill 槽的指令结果由 `EnsureReg` 发射 `GETL` 恢复。
5. `_currentDef` 让 `EnsureReg` 区分“定义”（必须分配真正的目标寄存器）与“使用”
   （可以从槽恢复），避免在定义处从尚未写入的槽读取。

**边界**：

- 不改操作码、VM、`.isb` 头部或调用约定；只新增既有的 `SETL` / `GETL` 指令与帧槽。
- 没有 spill 槽的指令结果仍不能丢弃；它们不跨调用活跃，受 SSA 支配关系保护。
- 块边界失效规则同步扩展：有 spill 槽的值也可在块边界丢弃并按需 `GETL`，
  不再依赖“定义块一定在寄存器里”的跨块复用。
- 该修复把 `RecursiveFunction_ReturnsFactorial` 从 `Skip` 恢复为 `120`；
  `StackArgPassingTests.LoopCarriedAccumulator_IsPreserved` 也从 `Skip` 恢复。

#### 6.3.9 函数调用实参个数不校验 + 命名实参路径编译期崩溃 `[已登记 2026-10-16 · 独立立项 · 登记时未改代码]`

**结论 `[事实]`**

前端把「位置实参 `i` → 声明序第 `i` 个形参」逐位绑定，但**不校验实参个数**。
函数声明 N 个形参而调用只给 M < N 个实参时，**零诊断**放行；IR 产出少于形参数的 `call`；
后端只给"已提供"的实参写 `A0..An`，缺失形参的 A 位保持原值，
而被调方仍按键位绑定到 `L0..Ln` 并当作实参使用：

- 缺失**标量**形参 ⇒ 静默取 `nil`（`0`）；
- 缺失**指针**形参（`VAR_OUTPUT` / `VAR_IN_OUT`）⇒ 静默把 A 位残留值当**槽号**解引用：
  首次调用为 `nil=0`（落到**被调方自身帧** slot 0），此前若有 ≥2 实参的调用则为**陈旧指针**
  （落到**调用方**任意帧槽）。两种都**不越界、不报错**，静默写错位置。

这不是有明确定义的"默认实参"机制，而是**调用契约没有被检查**。

#### 6.3.11 FB 实例寻址基准错误 ⇒ 实例成员可见性不可用 `[已裁定 2026-10-16 · 已登记 · 已修复 · 已验收]`

**背景**：§6.3.5 首行「FB 实例成员赋值可见性」原为**语义待裁定**。本片取证发现：
当前实现**不是「可见与否未定」，而是实例寻址基准错误** ⇒ 二者是两回事。现予裁定并登记。

**取证（只读，未改仓库；探针 P17 / P18，另参 P0）**

机制：后端的「指针」是**创建它的帧**里的相对槽号，`GETR`/`SETR` 以**本帧 `FP`** 解引用
（`addr = FP - 1 - slot`；§6.3.7 / `VMBase.RunLoop.cs`）。FB 的 `__instance` 由调用方传入的是
**调用方槽号**，但 §6.3.7 **刻意未对它重定基**
（`FunctionEmitter.NeedsRebase`，`:1387-1388`：`!(isFbCallee && argIndex == 0)`）。
于是 FB 主体以**自己的 `FP`** 减去**调用方槽号** ⇒ 落到 **FB 自己的帧**，而非调用方的实例。

对照实验（同一 FB：`VAR_INPUT a; VAR n;`，体为 `n := n + a; Print(n);`，连续三次 `f(1)`）：

| 探针 | `f` 在调用方槽 | 三次 `n` | 解释 |
| --- | :--: | --- | --- |
| P17 | 0 | **1, 1, 1** | 槽号撞上 FB 序言写入的槽 0（`SETL R4, L0`）⇒ 每次被覆写 |
| P18 | 3 | **1, 2, 3** | 槽号超出序言写入的槽 ⇒ 恰在 FB 帧内一处稳定地址上「碰巧持久」 |

P0 另证：调用方 `Print(f.n)` 恒为 `nil`（FB 从不写调用方的 `f`）。

⇒ **FB 成员读写从不落到调用方实例**；「状态持久」只是**调用方槽号是否撞上 FB 序言槽**的偶然结果，
既非「可见」、也非确定。

**裁定（2026-10-16 · 语言语义）**

FB 实例成员（`VAR` / `VAR_INPUT`）的读写**应当落到调用方的实例存储**（**双向可见**）：

- `VAR`：FB 主体与调用方对同一实例成员的读写应当可见；
- `VAR_INPUT`：属**实例状态** —— 显式传入时更新对应实例字段、省略时保留该实例
  上一次**已确定**的值、首次调用前用已裁定的**类型默认值**（§6.3.10）；
- **寻址机制**：设计必须解决 `__instance` 跨帧寻址，**不得继续把调用方槽号直接当作被调方帧槽号**；
- **不因此自动延伸**：`VAR_OUTPUT` / `VAR_IN_OUT` 的**省略 / 保留**规则**仍未裁定**。

**现状缺陷登记（本片只登记，不修实现）**

### 7.3 版本字段：**语义已冻结，字节布局未冻结** `[语义已冻结 / 布局待决]`

**三条语义（2026-10-15 冻结）**：

| # | 语义 | 不兼容时的强制行为 |
| --- | --- | --- |
| `FMT-v1` | **格式版本**不兼容 | **拒绝读取或链接** |
